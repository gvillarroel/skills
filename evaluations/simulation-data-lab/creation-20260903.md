# Simulation Data Lab creation and evaluation — 2026-09-03

## Objective

Create a self-contained Codex skill that can turn a user question into an
auditable simulation experiment, generate analysis-ready data, and support or
challenge hypotheses without presenting simulated evidence as empirical proof.

## Engine landscape and decision

No single engine dominates every simulation structure. The decision context for
this skill weights headless automation, transparent tabular outputs,
reproducibility, portability, and license-free execution more heavily than a
visual modeling IDE. Scores are a 1–5 author assessment against that context,
not vendor benchmarks.

| System | Automation and portability (25%) | Paradigm coverage (15%) | Scientific depth and scale (15%) | Data exploration fit (20%) | Reproducibility control (15%) | License friction (10%) | Weighted score |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Modular Python: standard library/NumPy/SciPy + SimPy/Mesa + SALib/PySD | 5 | 4 | 4 | 5 | 5 | 5 | 4.70 |
| Julia SciML ecosystem | 3 | 3 | 5 | 4 | 4 | 5 | 3.85 |
| Simulink/Simscape | 2 | 3 | 5 | 3 | 4 | 1 | 3.10 |
| AnyLogic | 2 | 5 | 4 | 3 | 3 | 1 | 3.10 |
| NetLogo/BehaviorSpace | 4 | 2 | 2 | 3 | 3 | 5 | 3.10 |

Decision:

- Use a modular Python adapter as the general default. It is the best fit for a
  portable, agent-authored, headless skill whose primary deliverable is
  explorable data.
- Prefer SciML for difficult ODE/SDE/DAE/DDE systems or high-performance
  trajectory ensembles when a Julia runtime is justified.
- Prefer an existing AnyLogic model when licensed multimethod DES + ABM + system
  dynamics and a visual enterprise workflow are requirements.
- Prefer an existing Simulink/Simscape project for control, embedded, or
  multidomain physical systems already governed by that toolchain.
- Prefer NetLogo when teaching, participatory modeling, or the NetLogo model
  ecosystem itself is central.

## Implemented contract

The skill is rooted at `skills/simulation-data-lab/` and contains:

- a strict experiment specification with explicit phase, simulation uncertainty
  mode, scenarios, design points, replications, assumptions, outcome units, and
  machine-readable hypothesis contrasts;
- a deterministic planner with stable semantic run IDs, 96-bit coupling IDs,
  SHA-256-derived seeds, scenario-order invariance, and paired or independent
  seed policies;
- a narrow Python `simulate(run)` adapter contract with exact engine/RNG version
  metadata and pre/post execution model hashes;
- a bounded local runner that retains failed and diagnostically invalid runs,
  rejects non-finite/schema-drifting output, and writes tidy core CSV tables;
- automatic per-design-point hypothesis analysis for paired, independent, and
  deterministic mean differences, plus explicit non-identifiability;
- an audit that independently recalculates hypothesis samples, effects, MCSEs,
  intervals, threshold decisions, aggregate status, and challenge reversals;
- a data dictionary and DuckDB starter queries exposing runs, outcomes,
  summaries, scenario factors, and design-point parameters.

The data choices follow columnar interoperability guidance from [Apache
Arrow](https://arrow.apache.org/docs/index.html) and direct analytical access in
[DuckDB's Parquet guide](https://duckdb.org/docs/current/guides/file_formats/query_parquet).
The v1 validator certifies the core CSV bundle; a large Parquet extension must
add its own hashed extension manifest and validator before it is called
auditable.

## Epistemic and safety boundaries

- Simulation conclusions are always conditional on model structure, inputs,
  parameter range, and diagnostics.
- The only result statuses are `supports-under-model`,
  `challenges-under-model`, `inconclusive-under-model`, and
  `not-identifiable-from-design`.
- Every executable v1 contrast must classify every design point as primary or
  challenge. A challenge point must differ parametrically from primary points.
- The analyzer, rather than an agent-authored JSON narrative, owns the numeric
  result. The validator rejects a canonically rewritten but fabricated status or
  estimate.
- A deterministic model receives no invented Monte Carlo interval.
- `--allow-incomplete` emits `ok=false`, `releaseEligible=false`, and exits 2;
  it is diagnostic evidence, never a release pass.
- Model adapters execute Python in process. The skill therefore permits only
  agent-authored or reviewed/trusted code and warns that imported dependencies
  and external files require additional provenance.

## Independent release audit and P1 closure

A separate read-only audit found five defects not covered by the initial 22-test
suite. They were treated as release blockers and fixed before handoff:

1. Inferential result comparison used Python equality, under which JSON `false`
   equals numeric zero and `true` equals numeric one. The validator now compares
   canonical JSON result bytes, and adversarial tests replace numeric zero/one
   leaves with booleans one at a time and require rejection.
2. Ordinary Python module loading could execute timestamp-valid stale bytecode
   while the manifest hashed newer source. The runner now reads, hashes,
   compiles, and executes the exact same reviewed `model.py` bytes and rejects
   source mutation. A same-size, same-mtime stale-`pyc` regression proves the new
   source behavior and manifest digest agree.
3. Observation and event `sim_time` values lacked a unit. Optional top-level
   `experiment.timeUnit` is now mandatory whenever either table has rows, is
   exposed to the adapter as `run["time_unit"]`, is repeated in each generated
   `time_unit` column, and is independently checked by the validator. Missing or
   tampered units are covered by adversarial tests.
4. Description or provenance metadata could make a value-identical challenge
   point appear distinct. The nonredundancy gate now compares only canonical
   parameter name-to-value maps; description-only and `sourceType`-only changes
   are rejected.
5. Independent run, outcome, and optional-row maxima allowed an unsafe Cartesian
   product. One `1,000,000`-row joint materialization ceiling now covers the run
   plan, run records, outcomes, maximum summaries, observations, events, and
   diagnostics. Planning rejects the former `100,000 x 100` case before
   allocation, and a small monkeypatched integration test proves optional rows
   consume only the remaining shared allowance without partial row publication.
6. A follow-up audit found that ordinary Python equality still allowed JSON
   `true`, integer `1`, and floating-point `1.0` to substitute for one another in
   schema-version, seed, and plan-manifest envelope fields. Experiment,
   execution-manifest, RNG, and hypothesis-report integer fields now require
   exact non-boolean integer types. Plan-manifest verification compares canonical
   observed bytes with canonical expected bytes, covering all counts and file-row
   counts. Adversarial tests exercise boolean and integral-float substitutions
   across each boundary.
