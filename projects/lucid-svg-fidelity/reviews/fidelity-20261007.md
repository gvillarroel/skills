# Lucidchart SVG fidelity review

Date: 2026-10-07. Scope: current `lucidchart-svg` compiler and final evaluation fixtures, saved actual Lucid editor captures from the native compatibility project, and current official Lucid documentation. This review distinguishes drawing appearance from logical diagram content, vector storage, and native editing.

The observed native reconstruction preserves the simple diagram's logical content well, while materially changing its presentation. Formal SVG artwork import without rasterization is the appropriate candidate for scalable artwork, but file-specific visual parity has not been measured. No defensible overall fidelity percentage is available.

## Current native compiler limits

The compiler reads graph JSON rather than rendering the SVG. It can preserve extracted axis-aligned boxes, supported solid node colors, literal labels, explicit ports, and endpoint topology. It cannot directly retain arbitrary SVG drawing detail.

- Node text uses Liberation Sans and centered alignment. Source font family, weight, anchors, baselines, rich spans, and outlined glyphs are not represented. Font size and text color survive only when extracted into the supported graph fields.
- Borders are always 1 px solid. Connectors are straight black 1 px lines with a destination arrow. Edge labels use black 14 px midpoint/top placement. Source dashes, widths, custom arrows, curves, and waypoints have no contract.
- Rectangle corner radii and arbitrary outlines are absent. Ellipses become documented native `circle` shapes with rectangular bounds; equal live outlines remain unverified.
- Source groups are flattened; all shapes are above all lines. A tight white page replaces the original page size, margins, and transparency. The two inspected page sizes change from 500 × 180 to 512 × 152, and 400 × 500 to 422 × 432.
- Opacity, gradients, clipping, masks, filters, embedded images, rotation/skew, animation, accessibility metadata, and arbitrary source attributes are outside the compiler contract. This is a compiler boundary, not a claim that Lucid's formal SVG importer always rejects them.

A revealing fixture limitation is that all four source connector paths have no explicit or inherited stroke or arrow marker. They are semantic edges through metadata but are not visible stroked lines. The compiler introduces four visible black connectors and target arrows. Thus complete graph recovery does not imply matching artwork. See the [SVG painting specification](https://www.w3.org/TR/SVG2/painting.html#SpecifyingStrokePaint).

The [independent native audit](native-audit.md) records exact bounds, colors, ports, hashes and package JSON comparisons; its [machine-readable evidence](../artifacts/data/native-audit.json) is retained locally.

## Documented SVG mode differences

Formal custom-shape import can preserve SVG vectors when rasterization is disabled. Canvas drag-and-drop treats the file as a regular image, and the editor can offer **Rasterize SVG Imports**. Preserved vector storage does not guarantee identical curves, fonts, or overlaps. [Lucid staff's scaling guidance](https://community.lucid.co/product-questions-3/how-can-i-scale-svgs-while-retaining-quality-7004/index2.html).

SVG embedded as a Standard Import image is converted to PNG before document inclusion. [Lucid's image reference](https://lucid.readme.io/docs/images-si). In the reverse direction, a support answer dated July 5, 2025 states that exported SVG text becomes vector paths rather than live text. Inspect a current actual export before treating that dated behavior as a current file guarantee. [Lucid's editable-text guidance](https://community.lucid.co/ideas/exporting-a-lucid-document-as-a-svg-with-editable-text-2974).

The [vendor evidence audit](vendor-fidelity-audit.md) distinguishes documented behavior, historical qualifications, and unsupported feature guarantees. Custom SVG library import has an account entitlement boundary. [Current shape-library help](https://help.lucid.co/hc/en-us/articles/14931750819476-Shape-libraries-in-Lucidchart).
