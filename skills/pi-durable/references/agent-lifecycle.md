Use this workflow for agents generated by the Pi console. The console carries
its own service resources; a created project carries its own operations CLI,
prompts, tools, verification contract, evolution engine and persistent state.
For generation and the workspace boundary, read [agent creation](agent-creation.md).
Keep external/custom services read-only unless their owning integration supports
management. Never infer ownership from a PID or overwrite a legacy project.

## Follow the actual state

`/durable` shows configured agents even when their owners are stopped. Select
one to open its operation menu. `/durable list` prints inventory and the chosen
folder; `/durable inspect <service/agent>` combines owner/work and verification
state. `/durable status [service]` also works for stopped managed owners.
The menu groups owner controls, quality/evolution and logs/registration.
Large inventories and action groups page before rendering, retain their exact
identifiers behind shortened labels, and keep creation/reconnection available
on every inventory page. This avoids stock-selector overflow in compact Pi
terminals.

| Action | Pi command | Result |
|---|---|---|
| Create/configure | `/durable new` | Review folder, purpose, model and event source before creating an independent owner. |
| Start/recover work | `/durable start <agent>` | Start the owned project and resume admitted durable work. |
| Pause admissions | `/durable pause <agent>` | Persist a pause of new messages/events and polling; accepted work drains. |
| Resume admissions | `/durable resume <agent>` | Resume polling and accept new work. |
| Observe | `/durable inspect <agent>`, `/durable jobs <agent>`, `/durable traces <agent>`, `/durable logs <agent>` | Inspect actual work, public evidence and bounded/redacted logs. |
| Verify duty | `/durable criteria <agent>`, `/durable verify <agent>` | Configure acceptance assertions, then verify an actual completed result. |
| Stop/restart | `/durable stop <agent>`, `/durable restart <agent>` | Drain before stopping the authenticated owner; preserve identity, work and history. |
| Recover ownership | `/durable recover-owner <agent>` | Recover only after exclusive state ownership can be proved. Never kill a stale PID. |
| Login startup | `/durable login <agent>` | Review, install, inspect or remove only the owned per-user login registration. |
| Evolve | `/durable evolve <agent>` | Open request, reflection, evaluation, promotion and rollback stages. |
| Archive/reconnect | `/durable archive <agent>`, `/durable connect` | Remove only a stopped registration; retain project/state and reconnect it later. |

Status inspects all live Harness tasks and unsettled submissions, including
child and retained background work. Active generation, queued tasks, running
processes and cumulative provider calls are distinct. No idle status check
starts a model. A running process or completed submission is not a quality pass.

Lifecycle mutations authenticate the exact owner nonce/configuration through
the private loopback API. Stop waits up to 30 seconds by default. A busy timeout
preserves work and leaves admissions paused; wait and retry, or resume. Explicit
pause survives restart. A successful normal shutdown preserves the pre-shutdown
pause policy, so a previously accepting owner can accept after a normal restart.
Local console cancellation stops waiting, not admitted work.

Paused message/event admission returns HTTP **503**. A drain deadline with
unfinished work returns **409**. These are different conditions; callers should
inspect the response instead of treating either as a completed task.

To deliberately cancel selected remote work, use `/durable abort <agent>` with
an optional `--job ID`. `--background` additionally includes retained background
work and requires explicit review. Stop/restart never select this option for
the user. All terminal mutation reviews default to Cancel, keep their actions
visible while scrolling and render paths literally. RPC retains structured
dialogs. Closing Pi leaves an admitted independent service running.

## Define and check the duty

New projects ship `verification-contract.json` disabled. Set a task-specific
goal and concrete assertions before enabling it. The editor accepts:

```json
{
  "version": 1,
  "enabled": true,
  "agentId": "reviewer",
  "goal": "Return the expected fixture identifier and avoid a success claim without evidence.",
  "assertions": [
    {"id": "fixture", "kind": "output-contains", "value": "FIXTURE-42"},
    {"id": "no-unsupported-claim", "kind": "output-not-contains", "value": "tests passed without running"}
  ]
}
```

Use `output-equals` for exact text, `output-json-equals` with a plain key-array
`path` and JSON `value`, or `workspace-file-equals` with a scoped relative path
and expected text. Verification executes no model, shell, script or regex from
the contract. Workspace checks observe current files; they do not prove which
actor created them. Select assertions that establish the actual duty rather
than a model's confidence or a generic nonempty answer.

`/durable verify <agent> [--job ID] [--submission ID]` binds the selected actual
admission/conversation, terminal submission, source-version evidence, output
hash and contract hash. Receipts distinguish `passed`, `failed`, `inconclusive`
and `unconfigured`. Missing, pending, offline, changed or unattributable work
never becomes a quality pass. Receipts and public verification evidence persist
for later inspection and reflection. These checks establish their configured
conditions; wider review quality requires an appropriate trusted verifier.

## Run a requested improvement cycle

1. Inspect actual execution traces and failed/passed duty receipts. Record an
   observable improvement goal, allowed prompt/task-tool/script paths and a
   trusted application-specific verifier with frozen fixtures.
2. Drain/stop the managed owner. Choose **Freeze model choices** in `/durable
   evolve <agent>` before a real study. The console resolves exact model/effort
   choices, saves catalog metadata and backs up the previous configuration.
   This makes no inference call and does not start the service. Keep the frozen
   configuration for the study and subsequent controlled release.
3. Request the bounded improvement in the evolution menu. Reflection export
   reads sanitized observable evidence; **Generate an inactive reflection
   draft** is a separate explicit model call without tools. It activates
   nothing. Import a complete candidate with evidence citations and exact source
   preimage hashes.
4. Evaluate baseline and candidate against the same frozen verifier and cases.
   Configured duty criteria, evaluator/fixtures and management/security code are
   protected. Core workspace and GitHub allowlist tools cannot be candidate edit
   targets. The bundled synthetic task-policy fixture demonstrates mechanics;
   replace it with the actual duty verifier before claiming useful quality gain.
5. Promote only the exact passing candidate while all work is drained and the
   owner is stopped. The console then builds and runs the project's offline
   smoke. A failure leaves the owner stopped. Startup stays explicit; run a
   representative task and verify its outcome after release.
6. On regression, stop/drain and roll back the exact promoted version. Rebuild
   and smoke before restarting. Use the recovery stage after an interrupted
   source transaction. Preserve rejected candidates, raw evaluation outputs,
   original source bytes and public decision/version lineage.

Events, PR text, workspace files and agent replies never authorize improvement
or activation. Do not store private chain-of-thought. Read the generated
`AGENTS.md` and [independent evolution contract](agent-evolution.md) for engine
inputs and runtime limits. Model reflection, a source patch and a measured
quality improvement are different outcomes.

## Operate without the console or skill

From a console-created project's own directory:

```text
node dist/src/console/control-cli.js status
node dist/src/console/control-cli.js start
node dist/src/console/control-cli.js pause
node dist/src/console/control-cli.js resume
node dist/src/console/control-cli.js stop
node dist/src/console/control-cli.js restart
node dist/src/console/control-cli.js logs
npm run verify -- inspect --config config.json --agent reviewer
npm run verify -- verify --config config.json --agent reviewer
npm run evolve -- history --config config.json --agent reviewer
```

Use the actual configured agent ID. Keep `managed-agent.json` and its host
digest with the project, preserve the initial scaffold manifest, and back up
state consistently. A recovered or relocated application needs its own updated
connection/target paths; copying a running SQLite database is not a backup.
Native login-service deployment remains per-user and requires its own reviewed
plan and OS validation; see [service lifecycle](service-lifecycle.md).

Managed login plans use the exact project `agent-host.mjs` entry, with its
authenticated owner protocol. Start follows the native registration once it is
installed, preventing a second detached owner. On macOS the managed plan
restarts unsuccessful exits, while a clean drained stop stays stopped. The
ordinary generic CLI service planner retains its existing behavior. Native OS
activation and plans are separate validation surfaces; do not claim a native
macOS launch from a plan rendered on Windows.

For isolated offline mechanics, generate a console with no existing service,
install/check its package, then import its documented `prepareAgentCreation`
and `createAgent` API with context `provider: 'faux'`. The created application's
exact source entry names are `src/verify-cli.ts`, `src/verification.ts` and
`src/console/control-cli.ts`. Use `npm run verify -- --help` and the control
CLI's `help` rather than guessing filenames. Its Node-only `src/console/client.ts`
exports `DurableClient`: construct it with `{id,name,configPath,dataDir,baseUrl}`,
use `snapshot(agentId)` to read `conversation.id`, and `send(agentId,message,
{requestId,waitTimeoutMs})` for `{receipt,submission}`. A paused `send` refuses
admission with status 503. Stable request IDs prevent a corrected local probe
from duplicating an admitted task. Stop all created owners in `finally` and
verify both the last-owner PID and the exclusive state lock before handoff.
